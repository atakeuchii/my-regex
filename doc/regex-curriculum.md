# 正規表現エンジン自作カリキュラム（Clojure / 6日）

> **ゴール**: 正規表現エンジンを Clojure でゼロから実装し、「なぜ RE2 や grep は爆発しないのに Perl 系は ReDoS で爆発するのか」「後方参照があると何が根本的に変わるのか」を、手で作って腹落ちさせる。
> **対象**: DBエンジニアとして検索・収集を担当し、LSM ストレージエンジンと全文検索エンジンを自作した人。パターンマッチングの一般理論（オートマトン）にここで触れる。
> **想定時間**: 平日 2〜3h + 週末多め、ゆるく6日。主目標に集中すれば十分回せる構成。

## なぜこれをやるのか（最初に読む）

普段あなたが「使う側」にいる `re-find` / `grep` / `LIKE` は、内部でだいたい次のことをやっている：

1. 正規表現文字列を **AST にパース**する
2. AST を **オートマトン（NFA）にコンパイル**する
3. 入力を1文字ずつ食いながら **ありうる状態の集合を同時に進める**
4. 受理状態に到達したらマッチ成立
5. キャプチャグループは「どの部分がどのグループか」を **追加で追跡**する

この骨格を自分で書くと、次の三位一体が腹落ちする：

> **正規表現 = 正規言語 = 有限オートマトン（Kleene の定理）**

そして実務に直結する問いに、実装レベルで答えられるようになる：

- なぜ `(a+)+$` のようなパターンが特定入力で指数爆発するのか（**ReDoS** の正体）
- なぜ RE2 / grep はどんなパターンでも入力長に対して**線形時間**を保証できるのか
- なぜ後方参照 `\1` があるとオートマトン方式では原理的に扱えないのか（照合が NP困難になる）

ストレージエンジンで「なぜ削除が即座に消えずtombstoneになるのか」が腹落ちしたのと、同じ種類の理解が手に入る。

### 最重要の設計分岐 — バックトラック vs オートマトン

正規表現エンジンには根本的に異なる2つの流派がある：

| | バックトラック方式 | オートマトン方式 |
|---|---|---|
| 代表例 | Perl / PCRE / Python `re` / Java `java.util.regex` | RE2 / grep / awk |
| やり方 | 候補を1本ずつ試しては戻る（再帰） | ありうる状態を**同時に**追跡 |
| 後方参照・先読み | できる（正規言語を超える） | 原理的に不可 |
| 最悪計算量 | 入力長に対して**指数的**（ReDoS） | 入力長に対して**線形**を保証 |

**このカリキュラムはオートマトン方式を主軸に作る**。線形時間の気持ちよさを先に作り、バックトラックと ReDoS は Day 6 で「対比として」触れる。この対比を実装で体験するのが、このプロジェクトの一番おいしいところ。

### Clojure でやる旨味（意識して使う）

- **NFA シミュレーションの「状態集合」が `set` にそのまま乗る**。入力を `reduce` で畳みながら「状態集合 → 次の状態集合」を写像していくのは関数型のど真ん中。WAL リプレイを reduce で書いたのと同じ気持ちよさ。
- **AST の分岐**が素直（`core.match` or 単純な `case`/`cond`）。コンパイラが読みやすく書ける。
- **不変データ構造が VM のスレッド分岐を綺麗にする**。thread のフォークが構造共有でタダ同然。
- **`test.check` で `java.util.regex` を参照モデルにできる**。ストレージで「自作 vs 素の `sorted-map`」の等価性を検査したのと**全く同じ手口**。ランダムなパターンと入力を生成し、自作エンジンと Java 標準の照合結果が一致するかを機械検査する。これが最高に効く。

## 全体アーキテクチャ

```
     正規表現文字列  "a(b|c)*d"
            │
            ▼  Day 1
     ┌───────────────┐
     │  Parser        │  再帰下降。優先順位を握る
     │  (再帰下降)     │  連接 < 選択| < 繰り返し*+?
     └───────────────┘
            │  AST
            ▼  Day 2
     ┌───────────────┐
     │  Thompson NFA  │  ε遷移でフラグメントを再帰的に組む
     │  Compiler      │
     └───────────────┘
            │  NFA
            ▼  Day 3
     ┌───────────────┐
     │  NFA Simulator │  ★白眉：状態集合を同時に進める（線形時間）
     │  (状態集合)     │  ε閉包 → 1文字消費 → 次の状態集合
     └───────────────┘
            │
            ▼  Day 5（キャプチャは NFA では返せない）
     ┌───────────────┐
     │  Pike VM       │  ★最難関：バイトコード + capture slot
     │  (bytecode)    │  greedy/lazy を命令の並び順で表現
     └───────────────┘
            │
            ▼  Day 6
     ┌───────────────┐
     │  対比：Backtrack + ReDoS │  なぜ爆発するかを数字で見る
     │  概念：subset construction(NFA→DFA) │
     └───────────────┘
```

**探索順の思想**: バックトラックが「1本の経路を深く試して行き詰まったら戻る（DFS）」なのに対し、オートマトン方式は「ありうる全経路を1歩ずつ同時に進める（BFS的）」。この頭の切り替えが Day 3 の山場。

## フェーズ1：フロントエンド（Day 1）

### Day 1 — 正規表現パーサ（文字列 → AST）

**目標**: 正規表現文字列を再帰下降でパースし、扱いやすい AST に落とす。

**この日にサポートする構文（最小集合）**
- リテラル 1文字（`a`）
- 任意1文字 `.`
- 連接（`ab`）
- 選択 `a|b`
- 繰り返し `*` `+` `?`
- グループ `( ... )`

**やること**
- 演算子の**優先順位**を文法で握る（弱い順に：選択 `|` < 連接 < 後置量化子 `* + ?`）。再帰下降の定石：

```
regex   := alt
alt     := concat ('|' concat)*
concat  := repeat*
repeat  := atom ('*' | '+' | '?')?
atom    := literal | '.' | '(' regex ')'
```

- AST ノードを設計。例：`{:op :char :ch \a}` / `{:op :dot}` / `{:op :concat :parts [...]}` / `{:op :alt :left .. :right ..}` / `{:op :star :body ..}` / `{:op :plus ..}` / `{:op :opt ..}` / `{:op :group :body .. :idx n}`。
- `+` は `body body*`、`?` は `body|ε` に**脱糖して星と選択に還元**してもよいし、専用ノードで持ってもよい（後者のほうが Day 5 の greedy/lazy 制御が素直）。方針をコメントで残す。

**概念**
- なぜ再帰下降で優先順位が自然に表現できるのか（弱い演算子を外側の関数に、強い演算子を内側の関数に置く）。
- グループには**キャプチャ番号**を採番しておく（Day 5 で使う）。開き括弧を読んだ順に 1, 2, 3…。

**Clojureヒント**
- パーサ状態は「残り文字列 + 位置」を持つのが素直。可変の `(atom {:s s :pos 0})` でもいいし、位置を引数で持ち回る純関数スタイルでもいい。REPL で叩きやすい後者がおすすめ。
- テストは「パース結果の AST が期待通りか」を `=` で見る。`(parse "a(b|c)*")` の戻り値を目視で1回固定してからアサートに落とす。

**チェックポイント**
- [ ] `a`, `ab`, `a|b`, `a*`, `(ab)+`, `a(b|c)*d` が正しい AST になる
- [ ] `|` と連接と `*` の優先順位が正しい（`ab|c` が `(ab)|c`、`ab*` が `a(b*)` になる）
- [ ] 括弧の対応が取れないなど不正入力で、落ちずにエラーを返す（例外 or `nil`）

## フェーズ2：オートマトン（Day 2–3）

### Day 2 — Thompson NFA コンパイラ（AST → NFA）

**目標**: AST を Thompson 構成法で NFA に変換する。ε遷移でフラグメントを再帰的に組み上げる。

**やること**
- NFA の状態表現を決める。番号付き状態 + 遷移表がシンプル：
  - `:char c → next-state`（文字を消費する遷移）
  - `:split → [s1 s2]`（ε分岐。入力を消費せず2方向へ）
  - `:match`（受理状態）
- Thompson 構成法：各 AST ノードを「入口状態と出口の“穴”を持つ**フラグメント**」にコンパイルし、再帰的に接続する。
  - `char c`：`c` 遷移1本のフラグメント
  - `concat a b`：a の出口を b の入口へ繋ぐ
  - `alt a b`：`split` で a/b の両入口へ分岐、両出口を合流
  - `star a`：`split` で「a へ入る／抜ける」を作り、a の出口を split へ戻す
  - `plus` `opt`：star と同じ部品の組み替え

**概念**
- なぜ ε遷移（`split`）を許すと構成が劇的に簡単になるのか（各部品が「1入口・1出口」の箱になり、合成が接続だけで済む）。
- Thompson NFA の状態数はパターン長に**線形**に収まる。これが後で効く。

**Clojureヒント**
- 状態を可変にせず、「フラグメント = `{:start id :out [dangling...]}`」を返しながら状態テーブル（`{id → transition}`）を積み上げる純関数スタイルが綺麗。`out` は「まだ繋ぎ先が決まっていない穴」のリスト。接続時にパッチする。
- 状態 id は `(atom 0)` のカウンタか、ビルダーを reduce で回して採番。
- 可視化があると理解が跳ねる：NFA を DOT 形式で吐いて Graphviz で描く小関数を書いておくと Day 3 のデバッグが楽。

**チェックポイント**
- [ ] `a` の NFA が「`a` 遷移 → match」になる
- [ ] `a|b`, `a*`, `(ab)+` の NFA を DOT で描いて、手で辿れる
- [ ] 状態数がパターン長にだいたい比例している（爆発していない）

### Day 3 — NFA シミュレーション（線形時間照合）★白眉

**目標**: NFA を「状態集合を同時に進める」方式でシミュレートし、入力長に対して線形時間で bool 判定する。**このプロジェクトの中核**。

**やること**
- **ε閉包 (epsilon closure)**：ある状態集合から `split`（ε遷移）だけで到達できる状態を全部集める。`(a*)*` のような形で**無限ループに落ちない**よう、訪問済み集合で枝刈りする。
- シミュレーション本体：
  1. 開始状態の ε閉包を「現在の状態集合」とする
  2. 入力を1文字ずつ読み、各状態の `char` 遷移のうち**その文字に一致するもの**だけを進め、行き先の ε閉包を取って「次の状態集合」にする
  3. 入力を食い切った時点の状態集合に `:match` が含まれていればマッチ
- `reduce` で「文字 → 状態集合の更新」を畳む。まさに WAL リプレイと同じ形。

**概念**
- **なぜこれが線形時間なのか**：状態集合の大きさは NFA の状態数（＝パターン長オーダー）で頭打ち。各入力文字につき状態集合を1回更新するだけなので、**O(パターン長 × 入力長)**。経路が何本あっても集合に潰れるので爆発しない。← バックトラックとの決定的な差。
- ここでバックトラックの「1本ずつ試して戻る」から「ありうる全状態を集合で同時に持つ」への**発想の転換**が起きる。読み手にとっての最大の山場。

**Clojureヒント**
- 状態集合は `set`。ε閉包は「ワークリスト（stack/queue）+ 訪問済み set」で書く定番パターン。
- `reduce` の accumulator が状態集合。`(reduce step (eps-closure #{start}) input)`。

**test.check（ここで参照モデル検査を導入）**
- **参照モデル = `java.util.regex`**。ランダムに生成した「安全な部分集合の正規表現」と入力に対し、自作エンジンの bool 判定と `re-matches`／`re-find` 相当が一致することをアサート。
- パターンの生成器は Day 1〜3 でサポートした構文だけに絞る（後方参照・先読みなど Java 側にしかない機能はモデルから除外）。この切り分けがストレージの `sorted-map` 参照モデルと同じ発想。
- **数値は捏造しない**：もし「線形だから速い」と言うなら、`bench/` で入力長を振って実測し、時間が入力長に比例することを確認してから主張する。

**チェックポイント**
- [ ] `a(b|c)*d` が `"abccbd"` にマッチし `"abce"` にマッチしない
- [ ] `(a*)*` のようなε閉包で無限ループしない
- [ ] test.check で自作エンジンと `java.util.regex` の判定が数百〜数千ケース一致する ← **最初の大きな達成感ポイント**
- [ ] （任意）ベンチで入力長 n を振り、実行時間が n に比例することを実測

## フェーズ3：機能拡張（Day 4）

### Day 4 — 文字クラス・アンカー・量化子

**目標**: 実用的な正規表現に近づける。パーサと NFA の両方を拡張する。

**やること**
- **文字クラス** `[a-z]` `[^0-9]` `\d \w \s`：`char` 遷移を「1文字だが述語で判定」に一般化する（`{:op :class :pred (fn [ch] ...)}`）。範囲・否定・エスケープをパーサで解釈。
- **アンカー** `^` `$`：入力の先頭／末尾でのみ通れるゼロ幅遷移。`re-find` 的な「部分マッチ」との関係も整理（アンカーが無ければ暗黙に `.*?` で挟むか、開始位置を全走査するか）。
- **量化子** `{n}` `{n,}` `{n,m}`：パーサで展開。`a{2,4}` を `aa a? a?`（または NFA の複製）に脱糖するのが素直。**上限が無い `{n,}` は末尾を `*` に**。

**概念**
- 文字クラスは「アルファベットを1文字ずつ列挙した巨大な `alt`」と等価だが、述語で持てば状態爆発を避けられる。ここで「遷移ラベルを集合／述語で持つ」設計の効きが分かる。
- アンカーは「文字を消費しないが条件付きで通れる遷移」。ゼロ幅の概念（先読みの入口でもある）。

**Clojureヒント**
- 述語遷移にすると `char` 分岐が `(when (pred ch) ...)` に一般化されるだけで、Day 3 のシミュレータはほぼそのまま動く。差分が小さいことを味わう。
- `{n,m}` 展開は AST 段階でやると NFA 側を触らずに済む。

**チェックポイント**
- [ ] `[a-z]+`, `\d{3}-\d{4}`, `^abc$` が期待通り
- [ ] 拡張後も test.check（対 `java.util.regex`）が通る。生成器に文字クラス・アンカー・`{n,m}` を追加して回す
- [ ] 否定クラス `[^...]` とエスケープ（`\.` `\*`）が正しい

## フェーズ4：キャプチャ（Day 5）

### Day 5 — Pike VM とキャプチャグループ ★最難関

**目標**: 「どの部分文字列がグループ N か」を**線形時間を保ったまま**抽出する。単純な NFA は bool しか返せないので、Pike VM（バイトコード + capture slot 付き thread）へ移行する。

**やること**
- **バイトコード命令**を定義（Russ Cox Part 2 の命令セットが定番）：
  - `char c` / `class pred`：1文字消費、外れたら thread 死亡
  - `split L1 L2`：thread を2本にフォーク（ε分岐）
  - `jmp L`：無条件ジャンプ
  - `save n`：現在の入力位置を capture slot n に記録（グループ k の開始＝slot 2k、終了＝slot 2k+1）
  - `match`：受理
- **AST → バイトコード**にコンパイル（`my-regex.compile`）。グループの前後に `save` を挟む。
- **Pike VM 実行**：
  - thread = `{:pc 命令位置 :saves キャプチャ配列}`。同一入力位置で走る thread 集合を持つ。
  - **同じ pc に複数 thread が来たら先着を優先**（`pc` で dedup）。これが線形時間の肝。thread 数は命令数で頭打ち。
  - 入力1文字ごとに、現在の thread 集合を `split`/`jmp`/`save` で ε展開し、`char` で1文字消費して次の集合へ。

**概念 — greedy / lazy の意味論**
- greedy `a*` と lazy `a*?` の違いは、`split` の**2分岐の順序**で表現できる。先に「もう1回繰り返す側」を試すのが greedy、先に「抜ける側」を試すのが lazy。VM では **thread の優先順位（＝集合に入れる順）**で自然に決まる。これが VM 方式の美しさ。
- 「先着優先の dedup」と「split の順序」が組み合わさって、最左最長（greedy）／最左最短（lazy）のマッチが線形時間で出る。**このプロジェクトで一番難しいのはほぼ確実にここ**。焦らず、まず greedy のみ・キャプチャ1個から。

**Clojureヒント**
- capture 配列は不変ベクタで持つと、thread フォーク時のコピーが構造共有でタダ同然。可変配列で速度を出すのは Day 6 以降でよい。
- 実装ステップは細かく割る：①命令データ構造 → ②`a`（char+match）だけ実行 → ③`split` で `a|b` → ④`save` でグループ1個 → ⑤greedy `*` → ⑥lazy。1ステップずつ REPL で確認。

**test.check**
- 参照モデル（`java.util.regex`）の `Matcher#group(n)` と、自作エンジンのグループ抽出が**同じ部分文字列**を返すことをアサート。greedy/lazy を混ぜると差が出やすいので、ここでバグがよく捕まる（ストレージの Day 12 と同じ「バグが出たら勝ち」ポイント）。

**チェックポイント**
- [ ] `(a+)(b+)` が `"aaabb"` にマッチし、group1=`"aaa"` group2=`"bb"` を返す
- [ ] greedy `a.*b` と lazy `a.*?b` が `"axbxb"` で異なる結果を返す
- [ ] test.check でキャプチャ結果が `java.util.regex` と一致する ← **最大の達成感ポイント**

## フェーズ5：対比・仕上げ（Day 6）

### Day 6 — バックトラック / ReDoS / DFA概念 / まとめ

**目標**: もう一方の流派を実装して対比し、なぜオートマトン方式を選んだのかを数字で語れるようにする。人に見せられる状態に仕上げる。

**やること**
- **バックトラック版を簡易実装**：AST を再帰下降で「1本ずつ試して戻る」照合器にする（キャプチャは無しでよい）。数十行で書ける。
- **ReDoS を再現**：`(a+)+$` や `(a|a)*b` に `"aaaa...a"`（末尾不一致）を与え、**バックトラック版は入力長に対して指数的に遅くなる**が、**Day 3 の NFA シミュレータ／Day 5 の Pike VM は線形のまま**であることを `bench/` で実測。両者の時間を並べたグラフ or 表を作る。**数値は必ず実行して取る**。
- **DFA 概念（subset construction）**：NFA の「状態集合」そのものを1つの DFA 状態とみなすと、ε閉包を毎回計算せずに済み更に速くなる——という考え方をメモ。完全な DFA を先に作ると `.*a.{20}` で状態が指数爆発するため、RE2 は **lazy DFA（オンザフライ構築）**する。ここは実装は任意、概念理解が主。
- **README**：アーキ図、対応構文、バックトラック vs オートマトンの対比、ReDoS ベンチ結果、設計判断とトレードオフ。`my-regex.core` を薄いファサード（`match` / `find` / `groups`）として整える。

**概念**
- 「後方参照 `\1` はなぜオートマトン方式で扱えないのか」を言語化する（`\1` を含む照合は正規言語を超え、一般に NP困難。だから RE2 はサポートしない＝線形保証とのトレードオフ）。これが**実務で「この正規表現は grep で速いのに本番の言語だと遅い」に直結する知識**。

**チェックポイント**
- [ ] `(a+)+$` + 長い非マッチ入力で、バックトラック版が指数的に遅く、NFA／VM が線形であることを**実測データで**示せた ← **ReDoS の伏線回収**
- [ ] subset construction と lazy DFA の違い、なぜ完全 DFA を先に作らないかを自分の言葉で説明できる
- [ ] README だけ読めば設計と対比が分かる
